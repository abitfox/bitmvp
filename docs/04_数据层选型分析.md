# BitMVP 数据层选型分析：MySQL vs Supabase

> 日期：2026-09-04 ｜ 结论：**选 MySQL，你的判断是对的**
> 但理由不是「MySQL 比 Postgres 强」——而是三个现实因素压倒了技术优劣

---

## 一、先给结论

| 维度 | 判断 |
|---|---|
| **选型** | ✅ MySQL（自建，跑在现有服务器） |
| **版本建议** | 本地开发用 **8.0**；生产可沿用 5.7，但**建议新开一个 8.0 实例**（不要原地升级） |
| **兼容策略** | 统一用 **generated column** 建 JSON 索引，保证 5.7 / 8.0 一套 SQL 两边跑 |
| **丢了什么** | Realtime、Auth、Storage、pgvector → **都有替代方案，且都不难**（见第四节） |
| **风险点** | ⚠️ 服务器在境内还是境外？影响备案与海外 API 调用（见第六节，需你确认） |

---

## 二、为什么选 MySQL 是对的（三条现实理由）

### 理由 1：Supabase 在中国大陆是硬伤（这条最关键）

不是「慢一点」的问题，是**结构性缺陷**：

| 问题 | 实际情况 |
|---|---|
| **无中国大陆节点** | Supabase 托管版没有任何境内 region，所有查询都要跨境 |
| **延迟** | 国内访问 100–800ms 波动，晚高峰跨境链路易断流、超时 |
| **Realtime 断连** | 基于 PG 逻辑复制的实时订阅，跨境下断连是常态 |
| **合规红线** | 大陆 C 端用户个人信息出境存储违反《个人信息保护法》；无境内服务器则拿不到 ICP 备案 |

> 实测数据（2026-08-27，阿里云张家口节点探测）：supabase.com 中位加载 **5.2 秒**。

**这对 bitmvp.com 是致命的**——你的网站是给面试官当场打开的。如果首屏要等 5 秒，前面所有设计功夫都白费。

### 理由 2：你已经有整套基础设施，边际成本为零

| 你已有的 | 说明 |
|---|---|
| 服务器 + 宝塔面板 | 运维路径熟悉 |
| MySQL 5.7 | 已在跑，无需额外付费 |
| Node 24 + PM2 | CardEcho 已在这套栈上跑通 |

Supabase 免费层给你的是「不用运维」，但你本来就会运维、已经有服务器。
**用 Supabase 等于花钱买一个你已经有的东西，还附赠跨境延迟。**

### 理由 3：Web3 项目根本用不上 Supabase 最有价值的部分

这是很多人没想清楚的一点。Supabase 的四大卖点，逐个看：

| Supabase 卖点 | BitMVP 用得上吗 |
|---|---|
| **Auth**（邮箱 / OAuth / 魔法链接） | ❌ **用不上**。Web3 的登录是 **SIWE 钱包签名**，自己写约 50 行代码。Supabase Auth 是给 Web2 的 |
| **RLS 行级安全** | ❌ **用不上**。作品集没有多租户，且数据大多以钱包地址为主键，权限模型简单 |
| **Realtime**（PG 逻辑复制） | ⚠️ **可替代**。Radar 实时推送用 **SSE**（Server-Sent Events）足够，Node 原生支持，比 WebSocket 简单 |
| **pgvector**（向量检索） | ❌ **用不上**。Copilot 走的是 **MCP 工具调用**路线（调链上数据），不是 RAG 检索路线 |
| **Storage**（S3 兼容对象存储） | ⚠️ **可替代**。只有头像/logo 这类静态资源，直接放 `public/` 或服务器目录 |

**核心洞察**：Supabase 真正值钱的是「省掉后端开发」，但 BitMVP 的后端**本来就必须自己写**——
链上数据要聚合、要清洗、要缓存、要限流，这些活 BaaS 帮不了你。

## 三、一个更重要的认知：BitMVP 的核心数据不在你的数据库里

这是初学者最容易踩的坑——**想把链上数据全灌进自己的库**。别这么干。

```
┌─────────────────────────────────────────────┐
│  第 1 层：外部数据源（不落库，或短期缓存）        │
│  Alchemy RPC / CoinGecko / DexScreener       │
│  → 余额、代币列表、价格、交易历史                 │
└─────────────────────────────────────────────┘
                    ↓ 按需拉取 + 缓存
┌─────────────────────────────────────────────┐
│  第 2 层：缓存层（MySQL 表 + 内存 LRU）         │
│  token_meta_cache / price_cache              │
│  → 削峰、省 API 额度、提速                      │
└─────────────────────────────────────────────┘
                    ↓ 持久化
┌─────────────────────────────────────────────┐
│  第 3 层：业务数据（MySQL 唯一真相源）           │
│  用户 / 关注列表 / Copilot 会话 / 索引数据 / 埋点 │
└─────────────────────────────────────────────┘
```

> **先不上 Redis**。作品集阶段，Node 进程内 LRU + MySQL 表缓存完全够用。
> 多一个中间件 = 多一份运维负担，对求职 demo 性价比低。

## 四、丢掉的四个能力，怎么补

| Supabase 能力 | 替代方案 | 成本 |
|---|---|---|
| **Auth** | SIWE（Sign-In with Ethereum）钱包签名登录。前端 `viem` 签名 → 后端验签 → 发 JWT | 约 50–80 行 |
| **Realtime** | **SSE**。Next.js Route Handler 返回 `ReadableStream`，前端 `EventSource` | 约 30 行 |
| **Storage** | 静态资源放 `public/`；用户上传走服务器目录 | 0 |
| **pgvector** | 不需要。Copilot 用 MCP 工具调用，不用 RAG | 0 |
| **自动 REST API** | 自己写 Route Handler（本来就要写，因为要做聚合与限流） | — |

**SSE 为什么够用**：Radar 的「实时资金流」是**单向推送**（服务端 → 客户端），
双向通信的 WebSocket 是杀鸡用牛刀。SSE 还自带断线重连，代码量只有 WebSocket 的三分之一。

## 五、MySQL 版本：5.7 还是 8.0？

### 关键差异（对本项目相关的部分）

| 能力 | MySQL 5.7 | MySQL 8.0 |
|---|---|---|
| JSON 类型 | ✅ 原生支持 | ✅ |
| **Generated Column + 索引**（JSON 提速关键） | ✅ 支持 | ✅ 支持 |
| 函数索引（直接对 JSON 路径建索引） | ❌ | ✅ 8.0.13+ |
| 多值索引（JSON 数组索引） | ❌ | ✅ 8.0.17+ |
| 窗口函数 / CTE | ❌ | ✅ |
| 官方支持状态 | ⚠️ **2023-10 已 EOL** | ✅ |

### 我的建议：**用 generated column，不用函数索引**

虽然 8.0 写法更简洁，但 generated column **两边都支持**，好处是：
- 本地 8.0、生产 5.7 可以跑同一套 SQL
- 未来升级 8.0 零改动

```sql
-- ✅ 推荐：5.7 / 8.0 通用
ALTER TABLE onchain_events
  ADD COLUMN event_type VARCHAR(32)
    GENERATED ALWAYS AS (JSON_UNQUOTE(JSON_EXTRACT(payload, '$.event_type'))) VIRTUAL,
  ADD INDEX idx_event_type (event_type);

-- ❌ 避免：仅 8.0.13+ 支持
ALTER TABLE onchain_events
  ADD INDEX idx_event_type ((CAST(payload->>'$.event_type' AS CHAR(32))));
```

### 性能实测参考（阿里云社区，10 万条数据）

| 查询方式 | 耗时 |
|---|---|
| 直接 `JSON_EXTRACT` 全表扫描 | ~850ms |
| **虚拟列 + 索引** | **~3ms** |

> **280 倍差距**。所以：JSON 只存「不常查的元数据」，**高频查询字段必须抽成真实列或 generated column**。

### 生产环境升级策略

⚠️ **不要原地升级 5.7 → 8.0**。你的 CardEcho 在跑，升级有兼容性风险。

推荐做法：
```
服务器现有 MySQL 5.7  →  保持不动，继续服务 CardEcho
新开 MySQL 8.0 实例（宝塔可多实例 / 或 Docker 起一个） → 专供 BitMVP
```

## 六、⚠️ 需要你确认的一件事：服务器在哪？

这个会直接影响架构，请告诉我：

| 情况 | 影响 | 应对 |
|---|---|---|
| **服务器在境外**（香港/新加坡/美西等） | ✅ 最理想。访问 CoinGecko / Alchemy 顺畅，无需备案 | 直接用现有服务器 |
| **服务器在境内** | ⚠️ 两个坑：<br>① 需 ICP 备案，否则域名无法用 80/443 解析到境内 IP<br>② CoinGecko、部分 RPC 端点可能访问受限或超时 | 方案：<br>• 前端静态部分放 Vercel（免备案）<br>• Node 后端放境外服务器<br>• 或整站放境外（最省事） |

> 参考你已有的 `app.cardecho.cn`——如果那个部署顺畅，说明现有服务器对外访问 Web3 API 没问题，照搬即可。

## 七、BitMVP 数据库表设计（初版）

按模块划分，标注用到的 JSON 与索引策略。

### 用户与身份

```sql
-- 钱包即身份，无密码、无邮箱
CREATE TABLE wallet_users (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  address       VARCHAR(64)  NOT NULL COMMENT '统一小写',
  chain_type    VARCHAR(16)  NOT NULL DEFAULT 'evm',
  first_seen_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_seen_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_addr_chain (address, chain_type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### Radar：关注与标签

```sql
CREATE TABLE watch_addresses (
  id             BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_address   VARCHAR(64) NOT NULL,
  target_address VARCHAR(64) NOT NULL,
  label          VARCHAR(64) COMMENT '如 Smart Money #12',
  chain          VARCHAR(32) NOT NULL DEFAULT 'ethereum',
  created_at     DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_target (user_address, target_address, chain),
  INDEX idx_user (user_address)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### Copilot：会话与可观测性（面试亮点）

```sql
CREATE TABLE copilot_sessions (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_address  VARCHAR(64) NOT NULL,
  title         VARCHAR(128),
  created_at    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_user_updated (user_address, updated_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE copilot_messages (
  id         BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  session_id BIGINT UNSIGNED NOT NULL,
  role       ENUM('user','assistant','tool') NOT NULL,
  content    TEXT,
  payload    JSON COMMENT '工具调用参数/结果，结构不固定',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_session (session_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ⭐ 工具调用日志：这是 Copilot 模块的「可观测性」证据
--    面试时展示这个表，能证明你懂生产级 AI 应用不止是聊天框
CREATE TABLE copilot_tool_logs (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  session_id    BIGINT UNSIGNED NOT NULL,
  tool_name     VARCHAR(64) NOT NULL,
  params        JSON,
  status        ENUM('success','error','timeout') NOT NULL,
  latency_ms    INT UNSIGNED,
  error_msg     VARCHAR(512),
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_tool_created (tool_name, created_at),
  INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 链上数据缓存

```sql
CREATE TABLE token_meta_cache (
  chain            VARCHAR(32) NOT NULL,
  contract_address VARCHAR(64) NOT NULL,
  symbol           VARCHAR(32),
  name             VARCHAR(128),
  decimals         TINYINT,
  logo_url         VARCHAR(512),
  updated_at       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (chain, contract_address)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE price_cache (
  chain            VARCHAR(32) NOT NULL,
  contract_address VARCHAR(64) NOT NULL,
  price_usd        DECIMAL(30,10),
  change_24h       DECIMAL(10,4) COMMENT '百分比，正=涨',
  updated_at       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (chain, contract_address),
  INDEX idx_updated (updated_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### Radar 索引数据（重，按需）

```sql
-- 预计千万级，用分区表
CREATE TABLE onchain_transfers (
  id           BIGINT UNSIGNED AUTO_INCREMENT,
  chain        VARCHAR(32) NOT NULL,
  tx_hash      VARCHAR(80) NOT NULL,
  log_index    INT NOT NULL,
  block_number BIGINT UNSIGNED NOT NULL,
  from_addr    VARCHAR(64) NOT NULL,
  to_addr      VARCHAR(64) NOT NULL,
  token_addr   VARCHAR(64) NOT NULL,
  amount_raw   DECIMAL(65,0) COMMENT '原始整数，避免精度丢失',
  usd_value    DECIMAL(30,4),
  ts           DATETIME NOT NULL,
  PRIMARY KEY (id, ts),
  UNIQUE KEY uk_tx (chain, tx_hash, log_index, ts),
  INDEX idx_to_ts   (to_addr, ts),      -- 「谁在买入」
  INDEX idx_from_ts (from_addr, ts),    -- 「谁在卖出」
  INDEX idx_token_ts (token_addr, ts)   -- 「某代币的资金流」
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
PARTITION BY RANGE COLUMNS(ts) (
  PARTITION p2026q3 VALUES LESS THAN ('2026-10-01'),
  PARTITION p2026q4 VALUES LESS THAN ('2027-01-01'),
  PARTITION pmax    VALUES LESS THAN (MAXVALUE)
);
```

> **金额用 DECIMAL(65,0) 存原始整数**，不用 float。
> 这是 Web3 开发的基本素养——代币精度最多 18 位，`uint256` 最大值远超 BIGINT。

### 埋点

```sql
CREATE TABLE events (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_address VARCHAR(64),
  event_name   VARCHAR(64) NOT NULL,
  props        JSON,
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  -- generated column：5.7 / 8.0 通用，把高频查询字段抽出来建索引
  module       VARCHAR(32) GENERATED ALWAYS AS
                 (JSON_UNQUOTE(JSON_EXTRACT(props, '$.module'))) VIRTUAL,
  INDEX idx_module_created (module, created_at),
  INDEX idx_name_created (event_name, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 八、ORM 选型

| 方案 | 推荐度 | 说明 |
|---|---|---|
| **Prisma** | ⭐ 推荐 | 类型安全最好，schema 即文档，迁移工具成熟。**作品集里 schema.prisma 本身就是一份加分材料** |
| Drizzle ORM | ⭐⭐ | 更轻、SQL 味更浓、性能好。但生态和文档不如 Prisma |
| 裸 `mysql2` | 一般 | 控制力强但写起来啰嗦，不利于快速迭代 |

**建议 Prisma**。理由：
1. `schema.prisma` 可读性强，面试官扫一眼就懂你的数据模型
2. 类型安全对「基础不太行」的阶段是保护网
3. ⚠️ 注意：Prisma 对 **generated column** 支持有限，需要标记为 `@ignore`，或在 migration 里手写 SQL

## 十、一句话总结

> **Supabase 的价值是「让你不用写后端」，但 BitMVP 的后端本来就必须自己写——
> 链上数据的聚合、清洗、缓存、限流，BaaS 一样都帮不了你。
> 既然如此，不如用你已有的 MySQL，还顺带避开跨境延迟这个致命问题。**
