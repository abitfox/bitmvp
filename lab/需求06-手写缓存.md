## T1 · 429 的本质（0:00–0:50）

〔屏幕：上集 429 报错截图〕

> 治病先诊断。429 不是「你被拉黑」，是「这个时间窗口里你问太多次了」。那我到底问了多少次不必要的？回看上集的轮询：价格 60 秒内根本没变，我却每 5 秒问一遍——**九成的请求是白问的**。
>
> 诊断完了，处方也清楚：把答案留在手里，没过期就用。

## T2 · 为什么手写、不用 Redis（0:50–1:40）

〔屏幕：笔记卡「先问要不要，再问用哪个」〕

> 提到缓存，第一反应都是 Redis。我认真考虑了一下，最后决定手写，理由说给自己听：我的场景是单机、单进程，没有多服务共享缓存的需求；Redis 是个好服务，但为了 30 行能解决的事去部署运维一个服务，属于拿大炮打蚊子。
>
> 这也是这个系列的价值观：先搞清楚问题的最小尺寸，再选工具。

## T3 · LRU + TTL 原理（1:40–2:40）

〔屏幕：笔记卡两连「TTL：活多久」「LRU：满了挤谁」〕

> 缓存要回答两个问题：
> 1. **TTL（活多久）**：每个答案带个过期时间，过期就重新去问；
> 2. **LRU（满了挤谁）**：内存有限，满了就挤掉「最久没被用过」的那条——最近用过的，大概率还会用。
>
> 实现上有个偷懒妙招我查到了：JS 的 `Map` 会记住插入顺序，`get` 时把条目删掉重插一次，「最久未用」就永远沉在第一位——LRU 不用自己写链表。

## T4 · 30 行实现（2:40–4:00）

〔屏幕：`lab/labs/06-cache.ts`，现场敲〕

```ts
class Cache {
  #map = new Map();
  get(key) {
    const hit = this.#map.get(key);
    if (!hit) return null;
    if (Date.now() > hit.expireAt) { this.#map.delete(key); return null; }
    this.#map.delete(key); this.#map.set(key, hit); // 摸一下，浮到最新
    return hit.value;
  }
  set(key, value, ttlMs) {
    this.#map.set(key, { value, expireAt: Date.now() + ttlMs });
    if (this.#map.size > 200) this.#map.delete(this.#map.keys().next().value);
  }
}
```

> get 里三行：没命中返回空；过期删掉返回空；命中就「摸一下」挪到最新。set 里两行：写进去，超容量挤掉排头的。加上包装函数，30 行。

## T5 · 分层 TTL（4:00–5:00）

〔屏幕：笔记卡「TTL 不是拍脑袋，是按『数据变化速度 × 用户期待』」〕

> 每类数据的 TTL 我是这样估的：余额 15 秒——用户转完账希望马上看到变化；价格 60 秒——估值场景没人需要秒级价格，还省配额；ENS 名字 300 秒——它几乎不变。
>
> 同一个缓存，不同数据不同活法。这张表以后会进 BitMVP 成品（`cache.ts` 的 TTL 常量），今天先把数估出来，错了以后再调。
