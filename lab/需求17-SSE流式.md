# 需求 17《能活还不够，要逐字出：SSE 流式》策划案 · 思考流口播版

目标时长 7.5 分钟。视角铁律见 `lab/00-内容标准.md`。上集钩子：活了，但要傻等 15 秒。本集之后 Copilot 成型，AI 幕收官。

## 思考主线（先看骨架）

```
T1 傻等的真相：其实模型早就在出字 → T2 SSE：一条单向溪流 → T3 我的事件设计
→ T4 curl 直眼看流 → T5 前端打字机 → T6 AI 幕收官 + 大钩子
```

## T1 · 傻等的真相（0:00–0:50）

〔屏幕：傻等的页面 vs 模型后台实际逐字生成的示意〕

> 我先纠正自己的一个想当然：不是「模型想完才回复我」——模型的 API 本来就是**一个字一个字往外蹦**的，是我自己把接口写成了「攒完整段再返回」。15 秒的空白，一半是模型真的在算，另一半是我把已经到手的字攥在手里没放。
>
> 所以这一集其实是把我自己的水管接对：模型 → 我的接口 → 前端，全程开着闸。

## T2 · SSE：一条单向溪流（0:50–1:50）

〔屏幕：笔记卡「SSE：HTTP 上的单向推送，逐条事件」〕

> 技术选型没纠结多久：AI 场景是典型的「服务器 → 浏览器」单向持续输出，**SSE（Server-Sent Events）**就是为这个生的——普通的 HTTP 响应，`Content-Type` 换成 `text/event-stream`，服务器想发多少条就发多少条，发完再关。
>
> 我顺便比较了下 WebSocket：双向、要握手、要管连接状态——AI 回答用不上反向通道，SSE 够用且简单。选型第一原则再次生效：按问题尺寸选工具。

## T3 · 我的事件设计（1:50–3:00）

〔屏幕：字卡五种事件「text / reasoning / tool_call / tool_result / done」〕

> 光逐字不够——15 集说过，一轮回答里模型可能调好几个工具。如果全部糊成一坨文字，用户看到的就是一堆乱码。所以我把流拆成五种事件：
> - `text`：正文增量，一个词一个词推；
> - `reasoning`：模型的思考过程（前端折叠展示）；
> - `tool_call`：模型决定调工具了（前端亮出「正在查报价…」）；
> - `tool_result`：工具跑完了，结果给谁看一目了然；
> - `done`：收工。
>
> 设计完回头看，这五种事件就是把 14–16 集的整条执行链路**翻译给用户看**。

## T4 · curl 直眼看流（3:00–4:20）

〔屏幕：`curl -N` 直接打 chat 接口〕

> 前端还没写，我用 curl 先验货——`-N` 禁用缓冲：

```bash
curl -N http://localhost:3000/api/copilot/chat -d '{"message":"100 USDC 换 WETH 多少"}'
```

> 终端里事件一条条蹦出来：先 `reasoning`，再 `tool_call`，停两秒（真在读链），`tool_result`，然后 `text` 逐字滚屏，最后 `done`。（停顿）01 集我用 curl 看过 RPC 的真面目，今天用 curl 看 AI 的真面目——这系列的套路倒是自洽。

## T5 · 前端打字机（4:20–5:40）

〔屏幕：成品 `ChatPanel.tsx` 对话录屏〕

> 前端接住这五种事件：`text` 逐字上屏（打字机效果），`tool_call` 变成一枚「正在查报价」的状态条，`tool_result` 收起摘要，`reasoning` 折叠进「思考过程」。
>
> 体验对比：同样是 15 秒，改完之后第 2 秒就有字蹦出来——**用户感知的等待时长，取决于第一字节什么时候出现**，这个规律今天亲眼验证了。

## T6 · AI 幕收官 + 大钩子（5:40–6:10）

> AI 这条线通了：工具（14）、工具集与边界（15）、超时（16）、流式（17），Copilot 成了完整的功能。
>
> 但写到这我回头一看，台账上已经堆了十几个技术点：RPC、Multicall、精度、缓存、报价、费率、WETH、签名、扫块、function calling、SSE……散在 17 集里。是时候停下来，把这些东西装进一张图里看清楚彼此的关系。下一集：全系列唯一不写代码的一集。
